# RecallHSC cloud sync

RecallHSC works fully offline and without an account. Everything lives in the browser's `localStorage`.
Cloud sync is an **optional** extra: if a Supabase project is configured and the user signs in, their
library, progress, statistics and preferences are kept in step across devices. If no project is
configured, or the user never signs in, the app behaves exactly as before and makes no sync requests.

This document covers what is stored, how to set up the backend, how to check it, and how conflicts are
resolved.

---

## 1. What is stored remotely

| Table      | Contents                                                                                        | Key                               |
|------------|-------------------------------------------------------------------------------------------------|-----------------------------------|
| `essays`   | essay title, full text, type (`essay` / `creative`), content revision hash, edit counter, deletion marker | user, essay id                    |
| `progress` | which sentences are learned (a `0`/`1` string), current position, partial-sentence marker, game level / coins / map marks, reset counter | user, essay id, essay revision    |
| `stats`    | aggregate practice counters for one device (attempts, accuracy sums, words typed, best WPM, most-missed words, typo pairs, per-hour accuracy, per-mode totals) | user, essay id, device id         |
| `prefs`    | the user's settings document                                                                    | user                              |

**Not stored remotely:** raw keystroke timings, the per-keystroke typing log, the device-local recent
history (`hist`), or anything else not listed above. Each device keeps its own `hist`.

Every row also has `updated_at` (set by the server clock) and, where relevant, the id of the device
that last wrote it (a random id generated by the app; it is not a hardware identifier).

## 2. Privacy and security

* Data is stored in the Supabase project of whoever deployed this copy of RecallHSC (for the public
  site, the site owner's project). It is **not** end-to-end encrypted: the project owner can read it
  through the Supabase dashboard, as with any ordinary database.
* Data travels over TLS (HTTPS / WSS) between the browser and Supabase.
* Row Level Security (RLS) is enabled **and forced** on every table. Each policy only matches rows where
  `user_id = auth.uid()`, so a signed-in user can only ever see and change their own rows. The
  anonymous role has no table privileges at all, so the public key on its own can read or write
  nothing.
* `updated_at` is set by a database trigger, and the same trigger refuses any attempt to change a row's
  `user_id`.
* A user can delete all of their cloud data and their account at any time (section 9).

## 3. Create a Supabase project

1. Sign in at <https://supabase.com/dashboard> and create a new project. Pick a region close to your
   users (for HSC students, Sydney `ap-southeast-2`).
2. Wait for it to finish provisioning. Under **Project Settings → API** (or **Connect**) note:
   * the **Project URL**, for example `https://abcdefghijklmnop.supabase.co`
   * the **publishable key** (`sb_publishable_…`) or, on older projects, the legacy **anon** key.
     This key is designed to be public; RLS is what protects the data.
   * Do **not** copy the `service_role` / secret key anywhere in this repository (see section 5).

## 4. Apply the database migration

The schema is in [`supabase/migrations/20261124000000_recallhsc_sync.sql`](../supabase/migrations/20261124000000_recallhsc_sync.sql).
It is idempotent, so running it again is safe.

**Option A: SQL editor (no tools needed)**

1. Dashboard → **SQL Editor** → **New query**.
2. Paste the entire migration file and press **Run**.
3. Check **Table Editor**: `essays`, `progress`, `stats`, `prefs` and `recallhsc_schema` should exist,
   and each should show "RLS enabled".

**Option B: Supabase CLI**

```sh
supabase login
supabase link --project-ref <project-ref>
supabase db push
```

`db push` applies every file in `supabase/migrations/` that has not been applied yet.

The migration creates:

* the four data tables with length and format constraints (essay ids `^[A-Za-z0-9_-]{1,40}$`, titles up
  to 60 characters, text up to 200,000 characters, learned flags up to 20,000 sentences, stats and prefs
  documents limited in size);
* `(user_id, updated_at)` indexes for incremental pulls;
* the `updated_at` / ownership trigger;
* RLS policies (`select`, `insert`, `update`, `delete`, each `to authenticated`, each restricted to
  `auth.uid() = user_id`);
* `public.delete_my_account()`, callable only by signed-in users;
* a `recallhsc_schema` table recording schema version `1`.

## 5. Configure authentication

RecallHSC signs users in with a one-time email link or code, so there are no passwords to manage.

1. Dashboard → **Authentication → Sign In / Providers** → **Email**: make sure it is enabled.
   Keep **Confirm email** on. Magic links and one-time codes are both sent by this provider.
2. Dashboard → **Authentication → URL Configuration**:
   * **Site URL**: `https://timliniscool.github.io/recallhsc/`
   * **Redirect URLs**: add both
     * `https://timliniscool.github.io/recallhsc/`
     * `http://localhost:5179/recallhsc/` (local development, see `tools/serve.cjs`)
3. Optional but recommended: **Authentication → Emails → SMTP Settings**. Supabase's built-in mailer is
   heavily rate-limited and meant for testing; set up your own SMTP provider before real use. You can
   also edit the "Magic Link" email template here (for example to show the `{{ .Token }}` code as well
   as the link).
4. Optional: under **Authentication → Rate Limits** adjust the email send limits to suit.

If you deploy the site somewhere else (a fork, a custom domain), use that URL for the Site URL and
redirect URLs instead.

## 6. Connect the app to the project

The app reads its sync settings from `js/sync/config.js`. It has two fields:

```js
url: 'https://<project-ref>.supabase.co',   // Project URL
anonKey: 'sb_publishable_…',                // publishable (or legacy anon) key
```

Both are empty by default, which means **local-only mode**: sync stays switched off, no requests are
made to Supabase and nothing is uploaded. Fill them in and redeploy to turn sync on.

Both values are public by design and safe to commit. **Never put the `service_role` or any secret key in
the repository, in `config.js`, or anywhere in the site.** That key bypasses RLS and would give anyone
full access to every user's data. If it is ever exposed, rotate it immediately in the dashboard.

### Content Security Policy

The page's CSP (`<meta http-equiv="Content-Security-Policy">` in `index.html`) only lets the app talk to
this site's own Supabase project:

```
connect-src 'self' https://fcnqhlcumstgoyfovuzt.supabase.co wss://fcnqhlcumstgoyfovuzt.supabase.co
```

If you ever move to a different project, change both this line and `js/sync/config.js`, then run
`npm run stamp`.

## 7. Verify Row Level Security

[`tools/rls-check.mjs`](../tools/rls-check.mjs) is a dependency-free Node 18+ script that checks the
policies against a real project.

1. In the dashboard, **Authentication → Users → Add user → Create new user**, create two **test** users
   with an email and password (tick "Auto Confirm User"). Don't use real accounts. The script needs
   password sign-in only for these test users; the app itself uses email links and codes.
2. Run:

   ```sh
   SUPABASE_URL=https://<project-ref>.supabase.co \
   SUPABASE_ANON_KEY=<publishable key> \
   RLS_A_EMAIL=rls-a@example.test RLS_A_PASSWORD=... \
   RLS_B_EMAIL=rls-b@example.test RLS_B_PASSWORD=... \
   node tools/rls-check.mjs
   ```

   (PowerShell: set each variable with `$env:NAME = '...'` first.)

The script signs in as A and writes an essay, progress, stats and prefs row. It then checks that A can
read them back, that B can't select, update, delete, overwrite or insert rows for A, that A can't
hand a row over to B by changing `user_id`, and that anonymous requests can read and write nothing and
can't call `delete_my_account()`. Afterwards it removes A's test rows and restores A's prefs. It
prints a PASS/FAIL line for each check and exits with code 1 if anything fails. With any variable
missing it prints a "skipped" message and exits 0, so it is safe to run in CI without secrets.

You can also inspect the policies by hand under **Authentication → Policies**, or with SQL:

```sql
select tablename, policyname, roles, cmd, qual, with_check
from pg_policies where schemaname = 'public' order by tablename, cmd;
```

## 8. Testing with two devices

1. Serve the site locally with `node tools/serve.cjs` and open `http://localhost:5179/recallhsc/`. Use a
   second browser or a private window as "device 2" (each has its own `localStorage` and device id).
   A phone on the deployed site works too.
2. Sign in with the same email on both.
3. Try each scenario and sync both sides:
   * add an essay on device 1, and it appears on device 2;
   * learn sentences on both devices for the same essay, and both end up with the union;
   * edit the text on device 1 only, and device 2 receives the new text. Progress for the old text is
     not applied to the new text;
   * edit the same essay differently on both while offline, then sync. Each device keeps its own text
     and receives the other device's text as a separate essay titled "… (other device)";
   * delete an essay on device 1, and it disappears from device 2 (unless device 2 edited it in the
     meantime);
   * press "Reset progress" on device 1, and device 2's progress for that essay is reset too and can't
     bring the old progress back;
   * practise on both, and the statistics screen shows combined totals.
4. Check the browser console and the dashboard's **Table Editor** to see the rows.

## 9. Deleting cloud data and the account

The app's account panel offers **Delete cloud data and account**. It calls the database function
`public.delete_my_account()`, which deletes every `essays`, `progress`, `stats` and `prefs` row of the
signed-in user and then deletes their auth user. This cannot be undone. The data on the current device
stays in `localStorage`, so the user keeps their essays locally and can carry on in local-only mode.

A project owner can also delete a user from **Authentication → Users**; all their rows are removed
automatically, because every table references `auth.users` with `on delete cascade`.

## 10. How conflicts are resolved

All merge rules are pure functions in [`js/sync/conflict.js`](../js/sync/conflict.js) (fully documented
at the top of that file and covered by `tests/unit/conflict.test.cjs`). In short:

**Essay revisions.** Each essay has a `rev`, a 64-bit FNV-1a hash of its type and text (line endings and
trailing spaces ignored), and a `ver` counter that goes up on every text or type edit. Each device
remembers the last revision it synced for every essay (its *base*).

**Library**

| Situation                                              | Result                                                                |
|--------------------------------------------------------|-----------------------------------------------------------------------|
| Essay only on this device                              | Uploaded.                                                             |
| Essay only on this device, same text as a cloud essay with another id | Linked to the cloud essay instead of uploading a duplicate.  |
| Essay only in the cloud                                | Downloaded, unless this device deleted it and the cloud copy wasn't edited after that, in which case the deletion is pushed. |
| Same text on both                                      | Nothing to do. Title differences: the higher `ver` wins (tie: cloud title). |
| Changed only here since the last sync                  | Uploaded.                                                             |
| Changed only in the cloud since the last sync          | Downloaded.                                                           |
| Changed on both                                        | **Both texts are kept**: this device keeps its version (and uploads it), and the cloud version is saved as a new essay titled "… (other device)". |
| Deleted elsewhere, unchanged here                      | Removed here too.                                                     |
| Deleted elsewhere, but edited here                     | Kept and uploaded again (revived). Edited work is never deleted silently. |

**Progress** is stored per essay revision, so sentence flags are never applied to a different version of
the text. For the same revision:

* a "Reset progress" increments the essay's `epoch`; the higher epoch wins outright, so an older device
  can't undo a reset and a newer reset elsewhere clears this device's progress for that essay;
* with equal epochs, learned sentences are combined (a sentence learned on either device stays learned),
  the furthest position is kept, the furthest partial-sentence marker is kept (dropped if that sentence
  is learned), game level and coins take the maximum, map marks are combined (this device wins a clash),
  and "started" is true if either device started.

**Statistics** are never merged into one record. Each device uploads only its own totals (one row per
device), and the app adds them together for display: counters are summed, records such as best WPM
take the maximum, and recent history stays local to each device. Nothing is counted twice.

**Preferences**: if this device has unsynced settings changes they win; otherwise the cloud settings
win. Values of an unexpected type are ignored.

Timestamps (`updated_at`) come from the database server, so a device with a wrong clock can't win a
conflict by having a later date.
